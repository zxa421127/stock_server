# Stock Server Security Hardening Design

## Scope

Implement all confirmed remediations from the static audit. Device, browser, canvas, hardware, and other fingerprinting are explicitly excluded.

## Registration and contact verification

Registration uses two rate limits: per-IP and global. Every POST attempt consumes both quotas, regardless of success. Production fails closed when Redis is unavailable. A reusable CAPTCHA service stores only a keyed digest in the session, uses separate namespaces for administrator and registration flows, expires challenges, and consumes them after a verification attempt.

A two-step registration flow is used. Step one validates username, password, email/phone, CAPTCHA, and rate limits, then issues a contact challenge. Email delivery uses SMTP. SMS uses a generic signed webhook. At least one verified contact is required before a user and API key are created. If SMS is disabled, email remains the available channel. Codes are stored only as HMAC digests with expiry, resend cooldown, maximum attempts, and one-time consumption.

## Account and session security

Users gain `session_version`, `password_changed_at`, `email_verified_at`, and `phone_verified_at`. User sessions store the current version and are rejected when the database version changes. A user changing their own password increments the version and receives a fresh current session. Administrator password reset, account disable, or an explicit logout-all action increments the version and invalidates all existing sessions.

All authentication and recovery inputs receive minimum/maximum length and format validation. Passwords are bounded at 128 characters.

## API token migration

Legacy plaintext `api_tokens` records are revoked, never converted into active credentials. Production readiness rejects a database that still has active legacy tokens. Current API keys remain HMAC digests and cache entries are cleared on rotation or account-state changes.

## Query safety and resource controls

A provider-neutral query policy validates parameter count, key/value size, symbol count, field count, date span, and required filters before upstream calls. Existing plan limits `max_symbols_per_request` and `min_refresh_interval_sec` are enforced. Redis-backed per-user concurrency and refresh-interval leases fail closed in production.

DataFrame row count and deep-memory size are checked before JSON conversion. Cache entries have row, item-byte, and total-byte limits. Redis cache payloads have compressed and decompressed bounds.

## Upstream transport and errors

Production rejects non-HTTPS Tushare relay URLs. Optional relay allowlists restrict hostnames. Redirects are disabled for relay requests where the project controls HTTP calls. Public API responses return stable sanitized upstream errors and an event ID; detailed errors remain in server logs.

## Release and production readiness

The production preflight verifies registration verification channels, secure relay settings, schema/session columns, legacy token revocation, Redis, mTLS, secret quality, external workers, and non-public binding. Release packaging is whitelist-based and scans for `.env`, databases, virtual environments, IDE metadata, private keys, certificates, logs, caches, and credential-like values. Packages include a SHA-256 manifest and never include runtime data.

## Deliverables

- Full cleaned source package with code, tests, migrations, `.env.example`, security runbook, and no secrets/runtime database.
- Production package generated by the hardened release builder.
- Test report, change manifest, and SHA-256 checksums.
