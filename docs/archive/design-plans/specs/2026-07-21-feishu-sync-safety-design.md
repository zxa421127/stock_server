# 飞书同步安全收口设计

## 目标

将本地数据库确定为会员、Token、套餐、权限和审计信息的唯一权威源；会员飞书表改为“本地单向发布 + 受控新用户登记导入”，开盘啦竞价表继续保持“本地快照单向写飞书”。

## 现状问题

当前会员完整同步会先执行飞书→本地，再执行本地→飞书。飞书中的旧套餐、错误状态、错误授权时间或错误用户ID可能先覆盖正确本地数据，然后再被回写到飞书，形成“错误但一致”的结果。飞书→本地还会直接写 users、api_keys 和 subscriptions，绕过套餐操作、订单与审计流程。

## 权威边界

### 本地权威字段

以下字段只能由本地管理员页面和正式业务服务修改：

- 用户ID
- API Token及Token状态
- 用户启用/禁用状态
- 当前套餐、待生效套餐
- 套餐开始时间、截止时间
- 订单号、收款、操作类型、补偿天数
- 订阅结束原因和审计记录

### 飞书会员表定位

飞书会员表用于展示本地会员资料，并允许登记新用户。它不再直接控制既有用户资料、Token、状态或套餐。

### 飞书竞价表定位

飞书竞价表仅接收本地SQLite中的开盘啦正式快照，不提供反向同步。

## 会员表：本地→飞书

保留全量和单用户发布。使用“用户ID”作为唯一匹配键。发布字段包括用户资料、当前套餐、待生效套餐、状态、时间和备注等展示信息。

完整Token不再写入飞书。发布时将“授权码”字段写为空字符串，以清理历史残留Token。Token仅保存在本地数据库和用户中心。

## 会员表：飞书→本地

`sync_feishu_to_local()`改为“受控新用户登记导入”，规则如下：

1. 不读取或写入飞书“授权码”。
2. 不修改任何已有本地用户的用户名、手机号、邮箱、淘宝昵称、状态、Token或订阅。
3. 有效用户ID匹配到本地用户时，仅将本地权威字段回写到该飞书记录，不改本地。
4. 用户ID缺失或无效时，按手机号、邮箱、淘宝昵称进行唯一匹配：
   - 恰好匹配一个已有用户：不改本地，仅回写正确用户ID和本地权威字段。
   - 匹配多个用户：记录冲突并跳过，不创建、不修改。
   - 没有匹配：仅在手机号、邮箱、淘宝昵称至少一个非空时创建普通用户。
5. 新用户固定为 `active`，`register_source='feishu'`，本地生成API Token，但不创建套餐。
6. 飞书中的状态、套餐代码、授权时间、待生效套餐和Token状态全部作为展示值忽略。
7. 导入完成后直接更新原飞书记录，写回本地生成的用户ID和本地权威字段，避免新增重复行。

返回值仍为二元组，语义调整为 `(新增用户数, 关联已有用户数)`。

## 自动和手工同步

- 周期同步和 `/api/admin/sync/feishu` 只执行本地→飞书发布，不再自动执行飞书→本地。
- `sync_feishu_to_local()`保留为显式人工登记导入函数，只有管理员主动执行时才会读取飞书。
- 管理员接口返回文案改为“已触发本地→飞书同步”，避免误解为双向同步。

## 竞价表

竞价同步逻辑保持不变：读取当天正式快照，校验 `source_provider=kaipanla`、`data_quality=complete`、非fallback，校验39字段结构后追加写入飞书。不存在任何飞书→本地路径。

## 兼容性与迁移

- 不需要数据库迁移。
- 现有飞书会员表无需删字段；“授权码”字段将被清空并停止使用。
- 保留现有函数名和管理员路由，减少部署风险。
- 旧的完整双向同步调用在行为上变为单向发布。

## 验收标准

1. 本地→飞书payload不包含完整Token，且明确清空“授权码”。
2. upsert只按用户ID匹配，不按Token匹配。
3. 飞书修改既有用户的状态、套餐、授权时间、联系方式后，反向导入不得修改本地。
4. 飞书新登记用户可创建本地普通用户，生成本地Token，不创建订阅，并回写用户ID。
5. 重复或冲突联系方式不会错误创建或覆盖用户。
6. 周期同步和管理员同步接口不调用飞书→本地。
7. 竞价同步相关测试继续通过。
